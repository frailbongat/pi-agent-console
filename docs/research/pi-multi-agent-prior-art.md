# Reusable Pi multi-agent prior art

Research for [Find reusable Pi multi-agent prior art](https://github.com/frailbongat/pi-agent-console/issues/4), evaluated against the native-flow and supervision constraints in [Specify native Agent Console v1 for Pi](https://github.com/frailbongat/pi-agent-console/issues/1).

**Research date:** 2026-08-02. All source links below are pinned to inspected commits.

## Answer

There is no drop-in open-source package that provides Agent Console's complete target: a native in-session console, attach/detach into concurrent **full** Pi interfaces, and a local Supervisor that outlives any one Pi or terminal process. The closest product prior art is [`pi-agent-hub`](https://github.com/masta-g3/pi-agent-hub/tree/605a535d5b47a4826fa95088041a973758d56fe3): it already manages persistent full Pi sessions, attach/return, status, direct dispatch, restart/fork, and owned worktrees. Its central seam is tmux, however, and its dashboard is a standalone tmux TUI rather than a Pi extension overlay with the required empty-editor `←` flow.

The reusable prior art is therefore compositional rather than wholesale:

1. Use Pi's documented extension UI/input surfaces for the in-session console and empty-editor trigger.
2. Reuse RPC or SDK as session-control primitives, not as a ready-made concurrent Supervisor.
3. Adapt MIT-licensed process ownership, heartbeat, durable-state, and worktree safety patterns—especially from `pi-agent-hub`, `pi-subagents`, `pi-multiagent`, and selectively `pi-crew`.
4. Treat native full-interface handoff and durable Supervisor ownership as unresolved architecture seams; no inspected project demonstrates both together through a documented Pi extension interface.

This conclusion narrows later architecture work but does not choose the process substrate.

## Official Pi surface and boundary

Pi intentionally leaves subagents out of core and names tmux, extensions, and packages as the expected solution space; it likewise recommends tmux for observable background work ([philosophy](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/README.md#L491-L506)). Its MIT license permits adaptation with preservation of the notice ([license](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/LICENSE#L1-L20)).

Documented public building blocks relevant to Agent Console are:

- **Native extension UX.** `ExtensionUIContext` exposes raw terminal input interception, status/widgets, focused custom components and overlays, plus editor text inspection ([UI API](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/src/core/extensions/types.ts#L112-L210), [editor access](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/src/core/extensions/types.ts#L212-L237)). Extensions may also register configurable shortcuts ([shortcut API](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/src/core/extensions/types.ts#L1250-L1264)). This is enough to prototype the required rule: consume `←` only when `getEditorText()` is empty, otherwise leave normal cursor handling untouched; the compatibility shortcut can use `registerShortcut`.
- **Lifecycle/status observation.** Public extension events identify agent, turn, message, and tool start/end activity ([event types](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/src/core/extensions/types.ts#L698-L785)). These support heartbeat emission and deterministic operational status, but not by themselves a trustworthy semantic `Needs input` classification.
- **SDK.** `createAgentSession`, `createAgentSessionRuntime`, and `AgentSessionRuntime` are exported ([exports](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/src/index.ts#L196-L211)); the official programmatic example presents SDK sessions and names runtime replacement as the multi-session facility ([README](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/README.md#L457-L475)). But one `AgentSessionRuntime` owns one current session, and switching first aborts/disposes that session before applying the replacement ([runtime ownership](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/src/core/agent-session-runtime.ts#L67-L103), [replacement](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/src/core/agent-session-runtime.ts#L167-L224)). It is a host/session primitive, not a concurrent durable Supervisor.
- **RPC.** `pi --mode rpc` is the documented non-Node integration path and uses JSONL over stdin/stdout ([README](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/README.md#L477-L487)). It is suitable for controlling a Pi child process, but process ownership, reconnection, persistence, and UI handoff remain the caller's responsibility.
- **Official subagent example.** It spawns one separate Pi process per task, streams parallel progress, limits concurrency, and propagates abort ([example contract](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/examples/extensions/subagent/README.md#L1-L13), [parallel limits](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/examples/extensions/subagent/index.ts#L33-L36), [spawn](https://github.com/earendil-works/pi/blob/aa0ec808b970db31822e07835a46647cb51d9d66/packages/coding-agent/examples/extensions/subagent/index.ts#L294-L339)). It deliberately uses JSON mode and `--no-session`, so it is reusable delegation/stream-rendering sample code, not attachable full-session supervision.

### Native-handoff gap

The public extension UI can open an overlay and can preserve normal editor behavior, but the inspected `ExtensionContext` surface has no operation that rebinds the host's full `InteractiveMode` to an independently running session. The exported runtime replacement API tears down the current session instead of backgrounding it. Therefore the empty-editor trigger itself is supported prior art; **attach to another live Agent's complete native Pi UI and later detach back without stopping either side is not demonstrated through the documented extension API**. That seam needs a prototype and may require an upstream Pi interface or a reduced-fidelity fallback.

## Reusable patterns by concern

### Full-session lifecycle and attach/detach

`pi-agent-hub` is the only inspected project that treats each worker as an ordinary, persistent, user-attachable Pi interface rather than a bounded child task. Its architectural split—Pi owns conversation semantics, tmux owns process/terminal persistence, and the hub owns registry/control—is explicit ([design](https://github.com/masta-g3/pi-agent-hub/blob/605a535d5b47a4826fa95088041a973758d56fe3/README.md#L11-L24)). Reuse the lifecycle vocabulary and registry behavior even if later architecture work rejects tmux as the final substrate.

A key distinction for the specification: a saved Pi JSONL session is durable conversation state, not a running Agent. A runtime owner still has to hold or recreate the live process, terminal, IPC endpoint, and lease.

### Status and attention

`pi-agent-hub` combines heartbeat freshness with tmux existence/activity fallbacks and distinguishes waiting from acknowledged idle ([status algorithm](https://github.com/masta-g3/pi-agent-hub/blob/605a535d5b47a4826fa95088041a973758d56fe3/src/core/status.ts#L19-L46)). Its extension writes heartbeats from Pi lifecycle events and records Pi session identity ([heartbeat producer](https://github.com/masta-g3/pi-agent-hub/blob/605a535d5b47a4826fa95088041a973758d56fe3/src/extension/index.ts#L76-L128)). This is a strong reusable baseline for `Starting`, `Working`, `Completed`, `Failed`, and `Stopped` reconciliation.

`Needs input` must not be inferred merely because an agent stopped streaming. Hub itself keeps runtime status and producer-confirmed attention as independent axes ([attention rule](https://github.com/masta-g3/pi-agent-hub/blob/605a535d5b47a4826fa95088041a973758d56fe3/docs/FEATURES.md#L92-L100)). Agent Console needs an explicit protocol signal or deterministic rule, with idle/unknown represented separately internally even if the product presents only the required states.

### Background ownership and recovery

Three distinct ownership models appear:

- **tmux-owned processes:** proven for full interactive Pi sessions and manual recovery (`pi-agent-hub`).
- **detached child/controller:** proven for bounded RPC jobs (`pi-subagents`, `pi-multiagent`, `pi-crew`), but requires PID/process-group identity, IPC authentication, startup acknowledgement, terminal records, watchdogs, adoption/orphan policy, and idempotent cleanup.
- **in-parent SDK sessions:** simplest steering and rendering (`pi-agent-orchestrator`, `pi-dynamic-workflows`), but cannot satisfy survival of console or shell closure without moving ownership into a separate Supervisor process.

Do not equate `detached: true` with supervision. `pi-crew`'s accumulated orphan registry, kill ordering, watchdog, and crash-log handling demonstrate the additional machinery required. Conversely, do not make parent-session shutdown cancel Agents as `pi-multiagent` does.

### Worktree ownership and cleanup

The strongest reusable worktree policy is `pi-agent-hub`'s: record explicit ownership metadata; validate branch names and collisions before creation; roll back partial multi-repo creation; reject finish/removal when either worktree or base checkout is dirty; and preserve a failed worktree ([creation/rollback](https://github.com/masta-g3/pi-agent-hub/blob/605a535d5b47a4826fa95088041a973758d56fe3/src/core/worktree.ts#L64-L122), [finish/remove guards](https://github.com/masta-g3/pi-agent-hub/blob/605a535d5b47a4826fa95088041a973758d56fe3/src/core/worktree.ts#L124-L180)). This aligns with Agent Console's “never auto-delete dirty work or unpushed commits” constraint better than subagent packages that automatically commit, merge, or prune temporary worktrees.

Additional hardening still needed for Agent Console: one active owner per checkout, durable reservation before process launch, atomic state updates, explicit finish/discard operations, unpushed-commit detection, and crash-recovery reconciliation between Git's worktree registry and Supervisor state.

## Constraints, hazards, and open questions

### Supported constraints

- A native overlay, persistent indicators, raw-key trigger, and configurable fallback shortcut are implementable with current public extension APIs.
- Concurrent model work is proven through both separate Pi processes and SDK sessions.
- Full Pi processes can be persisted and manually reattached through tmux; RPC children can be steered programmatically.
- MIT-compatible implementations exist for every individual kernel except the exact native attach/handoff seam.

### Hazards

- **Host-process coupling:** any manager held in extension memory dies with that Pi process.
- **False liveness:** stale heartbeat, live PID, tmux existence, and model activity are different facts; reconciliation needs precedence and timestamps.
- **Split ownership:** process, session file, worktree, and UI attachment need separate leases; a single session ID is not sufficient proof of ownership.
- **IPC loss/duplication:** polling a replaceable file or unacknowledged terminal injection is not enough for ordered dispatch. Use message IDs, atomic append/write, acknowledgement, replay, and bounded retention.
- **Destructive cleanup:** automatic commit/merge/remove behavior in subagent tools is unsuitable for user-owned long-lived Agents.
- **Unlicensed source:** `pi-command-center` may inform behavior, but its code should not be copied without an explicit license grant.
- **Dependency substitution:** adopting tmux solves persistence and terminal attachment but changes the product's dependency and native-flow story; hiding tmux behind a package overlay does not make the handoff a documented Pi-native operation.

### Open questions for later tickets/prototypes

1. Can a Pi extension safely suspend its overlay/current renderer and bind the same terminal to another already-running `InteractiveMode` using only documented exports, without tearing down either session?
2. If not, what upstream Pi host API is minimally required: runtime detach/rebind, terminal renderer handoff, or an attachable RPC/TUI transport?
3. Can the Supervisor reliably adopt an ordinary saved/running Pi session without risking two writers to one session file?
4. Which substrate meets closure, sleep, reboot-record, and no-remote-listener requirements with the smallest recovery state machine: tmux, a launchd/systemd-style user service, or a package-owned detached daemon?
5. What explicit child signal defines `Needs input`, and what conservative state is shown when the signal is unavailable?
6. Which Pi configuration/resources are safe to inherit verbatim in RPC/SDK children, and which must be re-resolved per project or dispatch?

## Implication for specification work

Carry forward `pi-agent-hub` as the behavioral baseline for full-session lifecycle, registry/status, and worktree safety; use official Pi APIs as the authority for native UX; and use the RPC/SDK projects as implementation pattern libraries. Do not adopt any candidate wholesale or treat a bounded “subagent” as the domain **Agent**. The next architecture decision should compare Supervisor substrates and explicitly resolve the native renderer handoff gap before promising full-fidelity attach/detach.
